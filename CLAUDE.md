# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Panel administrativo SUPRICOM. Next.js 16 (App Router) + TypeScript + MySQL + Odoo (JSON-RPC) + Socket.io. Multi-rol, multi-idioma (es/en).

## Comandos

- `pnpm dev` → `node server.js` (servidor custom: arranca Next **y** Socket.io + cron). **NO** usar `next dev` ni `next start`; el arranque pasa siempre por `server.js`.
- Producción: `pnpm build` y luego `pnpm start` (`NODE_ENV=production node server.js`).
- Gestor de paquetes: **pnpm** (Dockerfile y docs usan pnpm; existen `package-lock.json` y `pnpm-lock.yaml` duplicados, ignorar el de npm). `pnpm-workspace.yaml` solo configura permisos de build, **no** es un monorepo.
- Typecheck: `npx tsc --noEmit`. OJO: `next.config.mjs` tiene `typescript.ignoreBuildErrors: true`, así que `next build` NO valida tipos.
- No hay suite de tests ni ESLint configurado (`eslint` no está en devDependencies → `npm run lint` falla). No inventar comandos de test/lint.

## Arquitectura

- **Todas** las páginas viven bajo `app/[locale]/...` (next-intl). `middleware.ts` hace routing i18n + verificación JWT (jose) + guard por rol.
- Estructura espejo por rol/dominio: cada área (`adminleads`, `compras`, `vendedores`, `superadmin`, `gerente_venta`, `gerente_operaciones`, `recursos_humanos`, `dashboard`, `rma`, `cxc`…) suele tener su carpeta en `app/[locale]/`, sus endpoints en `app/api/`, sus componentes en `components/` y su lógica compartida en `lib/`. Al añadir una feature, seguir ese patrón de cuatro capas.
- `components/ui` es shadcn/Radix (ver `components.json`); reutilizar esos primitivos en vez de crear nuevos.
- i18n real: `i18n.config.ts` (rutas es/en, default `es`) + `i18n/request.ts` (conectado en `next.config.mjs`), traducciones en `messages/`. Los archivos raíz `next-intl.ts`, `intl.config.ts` y `next.intl.config.ts` están **obsoletos/sin usar**.
- Datos: MySQL vía pool en `lib/db.ts` (helper `query()` con `db.execute`). Odoo vía JSON-RPC en `lib/odoo.ts`.
- Auth: `POST /api/auth/login` autentica contra Odoo (email+password), luego busca el rol en MySQL (`users_config` JOIN `roles`, tabla `sellers` para `activo`), emite cookie httpOnly `token` (JWT, 7 días).
- **JWT library split**: `lib/jwt.ts` firma con `jsonwebtoken`; `middleware.ts` verifica con `jose`. Ambos deben compartir el mismo `JWT_SECRET`. Si cambias uno, cambia el otro.
- Roles/permisos se comparan en minúsculas en `middleware.ts`. **Cuidado**: los strings de `UserRole` (`lib/types.ts`) tienen casing inconsistente (ej. `"Gerencia De Ventas"` vs `"recursos humanos"`), pero `middleware.ts` aplica `.toLowerCase().trim()`. La lista de rutas de página protegidas es `isProtectedPath` en `middleware.ts` (una sección nueva en `app/[locale]/` hay que agregarla ahí o queda pública). Al añadir un rol hay que tocarlo en `middleware.ts`, `lib/types.ts` (`UserRole` + `rolePermissions.sections`) y `lib/actividades/rolesConfig.ts`.
- **Las APIs no pasan por el guard de sesión**: para `/api/*` el middleware solo corre `verificarOrigenApi()` (chequeo de Origin en métodos de escritura). Cada `route.ts` debe autenticarse sola con `requireRoles(request, [...])` o `requireSession(request)` de `lib/auth/roles.ts` (superadmin siempre entra). Un endpoint nuevo sin guard queda abierto.
- Dominio del portal de clientes (`PORTAL_HOSTS`, default `servicio.supricom.com.ve,soporte.supricom.com.ve`): ahí solo se sirve `/servicio-tecnico`; cualquier otra página responde 404 a propósito. Lo mismo con el dominio del servicio de notas de crédito para clientes (`NC_HOSTS`, default `notas.supricom.com.ve`): solo `/<idioma>/notas-credito/...`, reescrito a `app/[locale]/credito-clientes/` (ver la nota de RMA más abajo). Para que funcione hay que crear el DNS y agregar el dominio en EasyPanel.
- `server.js`: cron de KPIs Mié/Vie 20:00 America/Caracas → `GET /api/cron/calculate-kpis` con header `Authorization: Bearer $CRON_SECRET`. Emite `kpis_updated` por Socket.io; la URL del socket en el cliente sale de `NEXT_PUBLIC_SOCKET_URL` (`lib/socket-client.ts` / `lib/socket-emit.ts`).

Gotchas:
- `JWT_SECRET`/`ODOO_API_KEY` no tienen fallback hardcodeado: `lib/secretos.ts` falla cerrado (secreto aleatorio de un solo uso / string vacío) si la env var falta, y loguea el error. No reintroducir un fallback fijo — es lo que este archivo reemplazó.
- **Idioma de Odoo**: `callOdooRPC*` (`lib/odoo.ts`) manda `context.lang = "es_VE"` en toda llamada que no diga otro idioma. Sin eso la API usa en_US, y en los campos traducibles (nombre de producto, diario, cuenta, plazo, unidad…) la versión en_US es una copia vieja: la gente corrige en Odoo en español y solo cambia la es_VE (oct-2026: 354 productos distintos; PBB201 salía "ALTAVOZ…" siendo un power bank). No pasar `lang: "en_US"` salvo para leer la copia vieja a propósito (reglas de Spiff por nombre en `lib/spiff/calculo.ts`). Las copias del nombre que guardan Banco de Flyers y RMA se corrigen con `GET`/`POST /api/superadmin/productos/nombres` (`lib/productos/nombresOdoo.ts`; GET solo cuenta).
- Plazos de pago (`account.payment.term`): sin `context.lang` la API devuelve el nombre en inglés, que quedó viejo en varios plazos (el "30 días" en español es "21 días (copia)" en inglés; "90 dias" es "30 Days"). Leer nombres con `nombresPlazos()` de `lib/cxc/credito.ts` (lang `es_VE`); para días exactos, `invoice_date_due − invoice_date`.
- `target_company_id` (cids) en agentes/reportes: 9=Valencia (default), 10=Caracas, 7=Panamá (`lib/tools.ts`).
- Ninguna ruta desactiva la verificación TLS globalmente (`NODE_TLS_REJECT_UNAUTHORIZED`) — las que antes lo hacían (inventario ×3) usan `callOdooRPCInsecure()` en `lib/odoo.ts`, que aplica un `https.Agent({rejectUnauthorized:false})` scoped a esa llamada puntual, no al proceso.
- `META_ACCESS_TOKEN` es un token de **system user** con `instagram_basic` pero **sin** `instagram_manage_insights`: perfil y listado de publicaciones de Instagram funcionan, pero Insights (views, reach, profile_views, demografía, insights por publicación) devuelve `(#10) Application does not have permission`. `lib/instagram.ts` degrada por bloque (`{ available, reason }`) en vez de fallar; cuando Meta apruebe el permiso empieza a devolver datos sin cambiar código.
- Agente IA (`lib/agenteia/agente.ts`): lo usa el SuperAdmin y los usuarios que él habilite **por correo** en la tuerca de Configuración de la pantalla (tabla `agenteia_permisos`, se crea sola; `lib/agenteia/acceso.ts`, guardia `requireAgente()` en todas las APIs del agente; `agenteia_acceso`, la de antes por rol, quedó sin uso). Dos niveles: `consultor` (solo lee) y `editor` (además prepara y confirma cambios en Odoo; el SuperAdmin siempre lo es). Entran por `/agente-ia` (misma pantalla). **Qué ve cada rol** (pestaña de la tuerca, tabla `agenteia_roles`, se crea sola; `lib/agenteia/alcance.ts`, chequeo `node scripts/check-alcance-agente.cjs`): sede (todas / la de `cids`), "solo lo suyo" (filtro por el usuario de Odoo en cada modelo; modelo sin filtro = bloqueado) y áreas (ventas, cobranza, inventario, compras, costos, contabilidad, RRHH, leads, RMA, seguridad → modelos de Odoo y tablas del panel permitidos; sin "costos" se quitan los campos de costo/margen). Se aplica en el servidor, en cada herramienta; los roles limitados no tienen el MCP (SQL libre) y `consultar_panel` solo con todas las sedes, sin "solo lo suyo" y con tablas de sus áreas. Sin fila, cada rol usa `configPorDefecto()`. Cada cambio confirmado se anota antes de ejecutarse en `agenteia_cambios` (se crea sola, `lib/agenteia/bitacora.ts`; sin ese registro no se ejecuta; `jti` único = un botón no corre dos veces) y deja una nota en el chatter del registro con el nombre de quien lo confirmó, porque en Odoo el cambio queda a nombre del usuario de `ODOO_API_KEY`; el historial se ve en la misma Configuración. Usa Claude con herramientas propias de lectura de Odoo (read_group/search_read/search_count/fields_get por el JSON-RPC del panel; modelos con secretos bloqueados) y de la MySQL del panel (transacción `READ ONLY`). Si `ODOO_MCP_URL`/`ODOO_MCP_TOKEN` están definidas, suma además el MCP de Odoo (`rag_odoo_mcp_server`, conector MCP de la API de Claude, allowlist de lectura con SQL directo); con el módulo en modo API tokens va `ODOO_MCP_TOKEN` (key User, "Require API key" activo); con el módulo en modo OAuth (el de producción, lo usa el conector de claude.ai) no se define `ODOO_MCP_TOKEN`: el SuperAdmin autoriza una vez desde el enlace "Conectar SQL de Odoo" de la pantalla (`GET /api/superadmin/agenteia/oauth`) y `lib/agenteia/mcpOauth.ts` guarda el refresh token cifrado en `agenteia_mcp_oauth` (se crea sola) y renueva el access token cada hora; 30 días sin uso obligan a reconectar, igual que cambiar `JWT_SECRET`. Las escrituras nunca son directas: `preparar_cambio_odoo` devuelve un token HMAC que la pantalla muestra como botón, y solo al confirmar se ejecuta con `callOdooRPCEstricto()`. Las conversaciones se guardan por usuario en `agenteia_chats` (se crea sola; `app/api/superadmin/agenteia/chats`), con `localStorage` solo como copia local. **Supervisión** (`lib/agenteia/supervision.ts`, pestaña "Conversaciones de otros usuarios" de la tuerca, `GET /api/superadmin/agenteia/supervision`): el SuperAdmin lee las conversaciones de los demás; las de un SuperAdmin nunca salen, ni las de un uid sin correo conocido. Al guardarse una conversación de un no-SuperAdmin, un modelo barato (`AGENTE_IA_SUPERVISION_MODELO`, default `claude-haiku-5-5`) revisa los mensajes nuevos del usuario y deja alerta si el uso es ajeno a la empresa o sospechoso (tablas `agenteia_usuarios` y `agenteia_revision`, se crean solas; el costo de esa revisión no entra en `agenteia_consumo`). Si el último mensaje pide un archivo (Excel/Word/PDF/PowerPoint/HTML/código, regex `PIDE_ARCHIVO`) y el modelo no es Haiku, se suma la ejecución de código con las skills `xlsx`/`docx`/`pdf`/`pptx`; los archivos quedan en la Files API de Anthropic y se bajan por `GET /api/superadmin/agenteia/archivo?id=`.
- La MySQL de producción tiene allowlist por IP: no se puede conectar desde cualquier máquina de desarrollo.
- Las migraciones se corren a mano en el phpMyAdmin de EasyPanel (MySQL 9.7, base `supricom_panel`, usuario `root@'%'`). Ahí **no se puede leer `information_schema`** (`#1044 Acceso negado`) y hasta un `CREATE TABLE` sin la base delante falla. Por eso `sql/migrar_seguridad_completo.sql` "corre" sin agregar columnas. Los scripts para ese phpMyAdmin van con `supricom_panel.tabla` y sin `information_schema` (ej. `sql/egreso_por_etapas.sql`, `sql/recepcion_packing_list.sql`); MySQL no tiene `ADD COLUMN IF NOT EXISTS`, así que se verifica antes con `SHOW COLUMNS` y después con `SHOW COLUMNS` / `SHOW TABLES`.
- RMA: la nota de crédito **no** se pone a mano: RMA la pide (`POST /api/rma/nota-credito`, caso + producto + motivo) y queda en `rma_notas_credito`. En las sedes con el flujo activo (Valencia, Caracas y Panamá: mismo flujo, cambian las personas; activo = cada paso con al menos un responsable, `flujoCompleto`/`sedeConFlujo`) sigue el **flujo de aprobación** (`lib/notas-credito/`, pantalla común `/notas-credito`, APIs `/api/notas-credito/*`): RMA solicita → el equipo pasa a `nc_revision` → **preaprueba** (Rangel, rol `it`: entra directo a `/notas-credito`, `sql/insert_role_it.sql`) → **aprueba** (Gabriel Camacho; solo él aprueba, el SuperAdmin ve y configura pero no decide) → el equipo pasa a `nota_credito` y la orden le llega a quien **procesa** (Victor). Si Rangel o Gabriel rechazan, no procede y el equipo vuelve al estado que tenía (`estado_rma_previo`). RMA pide desde `/rma/nota-credito/solicitar` (caso + producto + por qué la NC + **por qué no se puede reparar**, obligatorio; los dos van juntos en `motivo`). Las NC que no son de RMA las crea **quien preaprueba** (los responsables de ese paso, o el SuperAdmin) con "Nueva nota de crédito": factura autocompletable → productos de la factura **agrupados por marca** (`spiff_brand_id`) → uno o más con su **serial de Odoo** (los move lines despachados al cliente de las `sale_line_ids` de la línea, menos los devueltos; sin lotes en Odoo se escriben a mano; un serial no va en dos NC) → motivo. El monto sale de las líneas (total con impuestos por unidad × cantidad), las líneas quedan en `nc_solicitud_lineas` (se crea sola) y la solicitud **nace preaprobada** (`por_aprobar`) y le llega a quien aprueba; al hacer el borrador en Odoo se dejan solo esas líneas, con los seriales en la descripción (`dejarLineasElegidas` en `lib/notas-credito/odoo.ts`). Quien procesa ya no crea solicitudes: hace en Odoo lo aprobado. **Cada paso ve lo suyo** (`puedeVerSolicitud` en `lib/notas-credito/acceso.ts`, pestañas de `vistasDe` en `tipos.ts`): preaprueba → las de RMA por preaprobar + las que creó/preaprobó/rechazó; aprueba → por aprobar; procesa → aprobadas y procesadas + NC de Odoo; rma → las de RMA de su sede. El SuperAdmin y quien aprueba tienen además "Todo el flujo" con filtro RMA / Preaprueba / Aprueba / Procesados (en Procesados se ve si la NC ya se creó en Odoo o no) y la pestaña de NC de Odoo. **El cliente también la pide, en un servicio aparte con su propio dominio** (`NC_HOSTS`, default `notas.supricom.com.ve`: ahí `/<idioma>/notas-credito/<sucursal>` se sirve desde `app/[locale]/credito-clientes/` —en el panel `/notas-credito` es la pantalla interna— y todo lo demás da 404; `lib/notas-credito/hostCliente.ts` + el middleware; mismo diseño que el portal de servicio técnico pero sin su correo; `lib/notas-credito/cliente.ts`, APIs públicas `app/api/credito-clientes/*` con límite por IP y captcha): factura + RIF (`resolverFactura` de `lib/servicio-tecnico/factura.ts`, la misma comprobación del reporte), productos por marca con su serial (misma `validarLineas` del panel), motivo de una lista (`MOTIVOS_CLIENTE`) + detalle, teléfono y correo. Entra como `origen = 'cliente'` en "Por preaprobar" y sigue el flujo; solo en sedes con el flujo activo. El cliente la sigue con su enlace (`nc_solicitudes.tracking_token`, 64 hex, `/<idioma>/notas-credito/<sucursal>/<token>`): ve la etapa, sus productos, el número de la NC de Odoo al final o el motivo del rechazo (quien rechaza lo escribe sabiendo que el cliente lo ve). **Nada público muestra precios ni montos.** Las columnas `motivo_tipo`, `contacto_telefono`, `contacto_email`, `tracking_token` se agregan solas (`columnasDelPortal` en `lib/notas-credito/datos.ts`); el token nunca sale en las respuestas del panel. Responsables por sede y paso: uno o varios **usuarios de `users_config`** que el SuperAdmin elige en la pestaña Responsables (tabla `nc_aprobadores`, por correo; el PUT rechaza correos que no estén en `users_config` y no deja una sede sin alguien en un paso si tiene NC en curso); Valencia arranca con los iniciales de `lib/notas-credito/datos.ts`. Hay además un paso opcional **RMA** por sede (RMA Valencia/Caracas/Panamá): no decide, recibe los avisos de sus solicitudes (aprobada, rechazada, hecha) y ve las notas de su sede; no cuenta para que el flujo esté activo. La pantalla muestra también las **solicitudes de RMA fuera del flujo** (`rma_notas_credito` sin fila en `nc_solicitudes`: anteriores al flujo o de sedes sin flujo activo) y las pendientes se pasan al flujo con "Pasar al flujo" (`lib/notas-credito/anteriores.ts`, `POST /api/notas-credito/anteriores`; SuperAdmin o quien procesa). **La lista es una sola** (Odoo y el panel manejan la misma data, se lee de Odoo en vivo, no se copia): *Todas* = las `out_refund` de Odoo del mes (`GET /api/notas-credito/odoo?mes=YYYY-MM`, `notasOdooDelRango`) + las solicitudes del mes que todavía no están en Odoo; una NC que salió de una solicitud es una sola fila (`nc_solicitudes.odoo_move_id`) y las hechas en Odoo sin pasar por el flujo salen "Hecha en Odoo, sin solicitud". *En curso* = solicitudes abiertas + NC en borrador en Odoo de cualquier fecha (`?borradores=1`). Victor la hace **en el panel o en Odoo, da lo mismo**: el panel usa el mismo asistente "Revertir" (`account.move.reversal` → `refund_moves`, ref "Reversión de: <factura>, motivo"), edita el borrador (líneas, Número de Control `nro_ctrl`, fecha) y publica; y si la hace en Odoo, `sincronizar()` la encuentra por `reversed_entry_id` (NC de la factura creada después de la solicitud y no vinculada a otra) y la sigue: publicada → `procesada`, anulada/borrada → vuelve a `aprobada`. No se publica si el total supera lo aprobado o falta el Número de Control. Tablas `nc_solicitudes`, `nc_eventos`, `nc_aprobadores` (se crean solas; referencia `sql/notas_credito_flujo.sql`). Correos: `N8N_NC_WEBHOOK_URL` (flujo propio "Notas de Crédito - Avisos", `aviso` = preaprobar/aprobar/procesar/rechazada/procesada); como n8n lee los destinatarios de `nc_aprobadores`, los iniciales se guardan en la tabla antes del primer aviso (`asegurarAprobadoresGuardados`). En una sede sin el flujo activo sigue siendo **solo la solicitud** al superAdmin (panel `/superadmin/rma-notas-credito` + correo `rma_nc_solicitada`), sin aprobación ni cambio de estado. Los PUT del caso y del producto rechazan poner `nota_credito`/`nc_revision`, y no mueven un equipo en `nc_revision` con solicitud abierta del flujo (`errorNotaEnCurso`); los `nc_revision` del flujo anterior se mueven a mano. Requiere `sql/rma_nota_credito_aprobacion.sql`. Si agregas un estado de RMA, hay mapas de etiquetas en `components/rma/estados.ts` (que usan `ProductosEnvio.tsx` y el detalle del caso), Seguridad (ingreso/despacho), la consulta pública y `lib/rma/emailActualizacion.ts`. - `leads.fecha_venta` es en realidad **fecha de cierre**: se puebla en todo lead cerrado, incluidos los `motivo_cierre = 'PERDIDO'`. Para contar ventas hay que filtrar además por `status = 'CERRADO' AND motivo_cierre IN ('VENTA','GANADO')`.
